# Internationalization

Spanish is the default locale at the root. English is a complete translation under `/en`. Every public page exists in both languages, and project URLs keep the same slug in both locales.

## Locale contract

| Locale | Prefix | Example home | Example project |
| --- | --- | --- | --- |
| Spanish (`es`) | none | `/` | `/work/todo-mcp/` |
| English (`en`) | `/en` | `/en/` | `/en/work/todo-mcp/` |

The locale types and shared values live in `src/i18n/locales.ts`. An unsupported locale prefix is not a valid route and falls through to the localized not-found page.

## Route map

| Route | Spanish | English |
| --- | --- | --- |
| Home | `/` | `/en/` |
| Work | `/work/` | `/en/work/` |
| Filtered work | `/work/?c=ia` | `/en/work/?c=ia` |
| Project detail | `/work/<slug>/` | `/en/work/<slug>/` |
| About | `/about/` | `/en/about/` |
| CV | `/cv/` | `/en/cv/` |
| Colophon | `/colophon/` | `/en/colophon/` |
| Not found | `/404` | `/en/404` |

Tier 1 and tier 2 projects have detail pages. Tier 3 projects appear in the catalog but do not have a detail route. Project slugs are shared by both locales; only the localized copy changes.

## UI strings

UI copy is stored in two typed dictionaries:

- `src/i18n/ui.es.ts`
- `src/i18n/ui.en.ts`

`UiStrings` is derived from the Spanish dictionary. The English dictionary uses `satisfies UiStrings`, so a missing key fails type checking. `src/i18n/ui.ts` exposes `getUi(locale)` and the complete locale map.

Use UI keys for navigation, filters, statuses, actions, empty states, form labels, page headings, descriptions, and accessible labels. Page and component markup must not contain hardcoded UI copy. Content-specific copy belongs in project YAML or MDX.

To add a UI key:

1. Add it to `src/i18n/ui.es.ts` with a neutral shape and Spanish copy.
2. Add the same key to `src/i18n/ui.en.ts` with English copy.
3. Read it through `getUi(locale)` in pages or components.
4. Run `npm run check` and `npm run validate:i18n`.

`validate:i18n` compares every leaf key recursively in both directions. A key present only in Spanish and a key present only in English both fail the check. The unit test in `tests/unit/i18n.test.ts` covers the same rule with small fixtures.

## Project content

Each project YAML has one shared metadata record and two required locale objects. The required objects are `locales.es` and `locales.en`:

```yaml
locales:
  es:
    title: ...
    summary: ...
    role: ...
    result: ...
    availability: ...
  en:
    title: ...
    summary: ...
    role: ...
    result: ...
    availability: ...
```

`availability` is optional, but the same locale keys must exist in both languages. Tier 1 case bodies use `<slug>.es.mdx` and `<slug>.en.mdx`. The content schema rejects a missing locale, and `validate:i18n` rejects an asymmetric project locale object even before Astro validates the collection.

To test the missing-translation failure with a fixture:

```sh
I18N_PROJECTS_DIR=/path/to/project-fixtures node scripts/validate-i18n.ts
```

The directory must contain the same YAML shape as `src/content/projects/`. Removing one English `summary` produces a `locale keys missing in English: summary` failure.

## Route helpers

`src/i18n/routes.ts` is the single route map. It exports:

- `routeHref(locale, route)` for building a localized URL.
- `parseLocalizedUrl(pathname, search)` for resolving a pathname and category filter.
- `switchLocaleHref(targetLocale, pathname, search)` for equivalent-language links.

```ts
routeHref('en', { name: 'project', slug: 'todo-mcp' });
// /en/work/todo-mcp/

routeHref('es', { name: 'work', category: 'ia' });
// /work/?c=ia

switchLocaleHref('en', '/work/todo-mcp/');
// /en/work/todo-mcp/
```

The helpers are covered by `tests/unit/routes.test.ts`. A project slug and a valid `c` query are preserved when switching locales.

## Language switcher

`src/components/shell/LanguageSwitcher.astro` renders one visible text link, with `hreflang`, `lang`, and a localized accessible label. Its server-rendered `href` comes from `switchLocaleHref`.

Static pages do not receive the runtime query string at build time. A small client script recalculates the link from `window.location.pathname` and `window.location.search`, so a filtered catalog such as `/work/?c=ia` switches to `/en/work/?c=ia`. The same script preserves project slugs.

No-JavaScript visitors still receive a valid link to the equivalent page without the client-side query refinement.

## Metadata

`src/components/shell/SeoHead.astro` emits localized metadata for every page:

- `<html lang="es">` or `<html lang="en">`
- localized `<title>` and `meta[name="description"]`
- canonical URL on the placeholder site origin
- reciprocal `hreflang="es"` and `hreflang="en"` links
- `hreflang="x-default"` pointing to Spanish
- localized Open Graph title, description, URL, and `og:locale` (`es_PE` / `en_US`)
- an alternate Open Graph locale
- Twitter card, title, description, and image metadata when an image is available

Canonical and alternate URLs omit runtime filters. The language switcher keeps the filter query, while search metadata points to the canonical work page.

## Verification

```sh
npm run check
npm run validate:i18n
npm run test:unit
npx playwright test tests/e2e/i18n.spec.ts
npm run build
```

The Playwright suite covers ES/EN route counterparts, project-page switching, filter-query preservation, reciprocal metadata, and the localized English not-found page. `npm run build` fails if a project or UI translation is incomplete.
